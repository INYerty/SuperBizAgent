# Spring 微服务架构：一次功能调用的执行顺序（详细笔记）

## 1. 一句话总览（从用户点击到结果返回）

一次“功能调用”（比如：下单、登录、查询订单）在 Spring 微服务体系里，通常按这个顺序走：

1. 客户端发起 HTTP/gRPC 请求
2. API 网关接入（路由/鉴权/限流/灰度）
3. 服务注册与发现 + 负载均衡（找到目标实例）
4. 目标业务服务的 Web 层入口（Filter → Interceptor → Controller）
5. 业务层 Service（事务、校验、编排多个下游）
6. 访问下游：数据库 / 缓存 / MQ / 其他微服务（可能有重试、熔断、降级）
7. 统一异常处理与响应包装
8. 结果返回网关 → 客户端
9. 全链路：日志、指标、链路追踪、审计、告警等同时发生

---

## 2. 请求进入系统前：DNS / TLS / 负载（可选但常见）

> 这一段是“微服务体系外壳”，你在云上/容器里几乎都会遇到。
> 
- **DNS 解析**：域名 → IP。
- **TLS 握手**：HTTPS 建立安全通道。
- **外部负载均衡（LB）**：把流量分配到多个网关实例（例如 Nginx / SLB / Ingress）。

---

## 3. API 网关层（Spring Cloud Gateway）执行顺序

网关通常承担“统一入口”的职责：

### 3.1 路由匹配

- 根据 Path/Host/Header 等规则，匹配路由：`/api/order/**` → `order-service`。

### 3.2 过滤器链（Gateway Filter Chain）

常见顺序（从前到后）：

1. **全局/路由级 Pre Filters（前置过滤器）**
    - 请求日志、Header 规范化、请求体大小限制
    - 认证（JWT 校验 / OAuth2）
    - 鉴权（RBAC/ABAC）
    - 限流（Redis Token Bucket / Sentinel）
    - 黑白名单 / 防刷
    - 灰度发布（按用户、Header、百分比路由）
    - 请求签名校验（ToB 场景常用）
2. **路由转发（核心）**
    - 选择目标服务（通过注册中心/静态配置）
    - 负载均衡选实例（见下一节）
    - 发起到下游的 HTTP/gRPC 调用
3. **Post Filters（后置过滤器）**
    - 响应日志
    - 响应头统一处理
    - 统一错误码映射
    - 指标采集

> 记忆点：网关就是一条“过滤器链”，核心动作是“选路由 → 选实例 → 转发”。
> 

---

## 4. 服务注册发现与负载均衡（Spring Cloud + Nacos/Eureka + LoadBalancer）

当网关/上游服务要调用 `order-service` 时，会发生：

1. **从注册中心获取实例列表**
    - Nacos/Eureka 返回：`order-service` 的实例 A/B/C（ip:port）。
2. **客户端负载均衡选择一个实例**
    - 常见策略：轮询、权重、最小连接数、基于响应时间、同机房优先等。
3. **构建真实下游地址并发起请求**
    - 例如从 `http://order-service/create` 解析为 `http://10.0.1.12:8080/create`。

> 注意：在 Spring Cloud 里，这些通常发生在 Feign/RestTemplate/WebClient 调用之前的拦截链里。
> 

---

## 5. 目标业务服务：从网络入口到 Controller

以 Spring Boot Web（Spring MVC）为例，典型进入顺序：

1. **Servlet 容器线程接收请求**
    - Tomcat/Jetty/Undertow。
2. **Filter 链（Servlet Filter）**
    - 例：CORS Filter、Spring Security FilterChain、TraceId 生成、请求体缓存等。
3. **Spring MVC DispatcherServlet**
    - 统一分发器。
4. **HandlerInterceptor（拦截器）**
    - `preHandle`（进入 Controller 前）
    - `postHandle`（Controller 正常返回后，渲染前）
    - `afterCompletion`（最终回调：无论异常/正常都会走）
5. **Controller 方法执行**
    - 参数绑定、校验（JSR-303：`@Valid`）、AOP 切面（日志/权限/幂等等）。

> 口诀：Filter（更外层，偏容器/安全） → DispatcherServlet → Interceptor → Controller。
> 

---

## 6. 业务层 Service：一次“功能”的核心编排

Controller 通常只做“输入输出”，真正的功能顺序多在 Service 内。

### 6.1 典型业务执行顺序

以“创建订单”为例：

1. **参数与业务校验**
    - 是否登录、商品是否存在、库存是否足够、价格是否被篡改。
2. **幂等性处理（强烈建议）**
    - 幂等号（Idempotency-Key/业务单号），避免重复提交。
3. **事务边界（本地事务）**
    - `@Transactional` 通常包住“本服务数据库写入”。
4. **调用下游（按依赖顺序）**
    - 读缓存/写缓存
    - 调用库存服务扣减库存
    - 调用支付服务生成支付单
    - 发送消息到 MQ（下单事件）
5. **领域事件/消息驱动的后续流程**
    - 订单创建后，异步触发：发券、积分、通知、物流等。
6. **返回结果**
    - 返回订单号、状态、下一步动作（如支付链接）。

### 6.2 AOP 在 Service 层常见的“穿插点”

- 事务（Transaction AOP）
- 重试（Retry）
- 熔断/限流（Sentinel/Resilience4j）
- 缓存（Cache AOP：`@Cacheable/@CacheEvict`）
- 权限/数据范围（Data Permission）
- 统一日志（Operation Log）

> 你可以把 Service 理解成“业务流程引擎（手写版）”：负责把多个组件按顺序串起来。
> 

---

## 7. 访问下游资源：DB / Cache / MQ / 其他微服务

### 7.1 数据库（MySQL 等）

常见顺序：

1. SQL 生成（MyBatis/JPA）
2. 连接池取连接（HikariCP）
3. 执行 SQL
4. 事务提交/回滚
5. 返回结果对象

注意点：

- 本地事务只能覆盖**单个服务的单库**（除非你上分布式事务方案）。

### 7.2 缓存（Redis）

常见顺序：

- 读：先查 Redis → miss 再查 DB → 回填 Redis（注意缓存穿透/击穿/雪崩）
- 写：先写 DB 再删缓存（或延迟双删），保证一致性策略

### 7.3 消息队列（Kafka/RabbitMQ/RocketMQ）

常见顺序：

1. 业务服务发送消息（事件：OrderCreated）
2. Broker 持久化/投递
3. 消费者服务收到消息
4. 消费者执行本地事务
5. ACK/提交 offset

注意点：

- MQ 不是“立刻执行”，而是把步骤拆成“异步后续”，用来解耦、削峰、最终一致。

### 7.4 调用其他微服务（Feign/WebClient/gRPC）

一次远程调用内部常见顺序：

1. 构造请求（序列化 JSON/Protobuf）
2. 传递上下文（TraceId、用户信息、请求来源）
3. 负载均衡选实例
4. 发起网络请求
5. 超时控制
6. 重试（可选，且要非常谨慎）
7. 熔断/降级（可选）
8. 解析响应（反序列化）

---

## 8. 容错链路：超时、重试、熔断、降级、限流（非常关键）

在微服务里，功能“执行顺序”经常会被容错组件改变：

1. **先设超时**：没有超时就没有稳定性。
2. **再谈重试**：只对“安全可重试”的请求重试（幂等 GET、或带幂等号的写）。
3. **熔断**：当下游持续失败，直接快速失败，保护系统。
4. **降级**：返回兜底数据/提示（例如“系统繁忙，请稍后再试”）。
5. **限流**：在入口或关键服务上控制 QPS，保护核心链路。

> 记忆点：超时是底线；重试要谨慎；熔断是止血；降级是兜底；限流是保护。
> 

---

## 9. 响应返回：异常处理与统一返回体

在业务服务返回前，通常还会走：

1. **统一异常处理**
    - `@ControllerAdvice` 捕获异常 → 转换成统一错误码、错误信息。
2. **响应包装**
    - 统一返回结构：`{ code, message, data, traceId }`。
3. **Interceptor afterCompletion**
    - 做请求耗时统计、清理 ThreadLocal。
4. **Filter 收尾**
    - 写访问日志、埋点、关闭资源。

然后响应回到：

- 上游服务/网关 → 网关的 Post Filters → 外部 LB → 客户端。

---

## 10. 全链路“伴随执行”的系统能力（几乎贯穿每一步）

这些不是某一个步骤，而是贯穿式能力：

### 10.1 日志（Logging）

- 入口生成/透传 TraceId
- 关键业务点打结构化日志（用户、订单号、耗时、结果）

### 10.2 链路追踪（Tracing）

- Sleuth/Brave/OpenTelemetry
- 每次跨服务调用都会产生 span

### 10.3 指标（Metrics）

- QPS、延迟 P95/P99、错误率、线程池、连接池、JVM

### 10.4 配置中心（Config）

- 动态开关：限流阈值、灰度开关、降级开关

### 10.5 安全（Security）

- JWT/OAuth2
- 权限校验
- 数据脱敏

---

## 11. 你可以用的“画图式记忆模板”

把一次调用抽象成三层：

1. **入口层**：LB/Ingress → Gateway（鉴权/限流/路由）
2. **业务层**：Controller → Service（事务/编排）
3. **资源层**：DB/Redis/MQ/其他服务（容错）

任何“功能执行顺序”问题，你都可以按这三层去拆解。

---

## 12.（可选）面试常问：为什么顺序要这样设计？

- 网关先做鉴权限流：把无效流量挡在最外面，保护后端。
- 服务内先做幂等再写库：避免重复写导致脏数据。
- 本地事务只包住本服务写库：保持边界清晰；跨服务用事件驱动/最终一致。
- 先超时再重试：否则重试会把系统拖死。

## 13. 按你用的组件，串成一条“真实调用链”（Nacos + Gateway + OpenFeign + Sentinel + Seata + RabbitMQ）

下面用一个常见写接口举例：**创建订单**（Order Service 作为入口服务），需要：扣库存（Stock Service）、记账（Account Service），并发消息给 MQ 做异步后续。

### 13.1 服务启动阶段（请求前置条件）

1. **各服务启动并注册到 Nacos**
    - 服务启动 → 读取配置（通常也来自 Nacos Config）
    - 把自己的 `serviceName + ip:port` 注册到 Nacos
2. **Gateway 启动并加载路由**
    - 路由可写死，也可从 Nacos/配置中心动态刷新
3. **OpenFeign 客户端准备就绪**
    - Feign 接口代理创建
    - 配套的 LoadBalancer、HTTP 客户端、编码/解码器准备
4. **Sentinel 规则加载（可动态推送）**
    - 限流/熔断/热点参数/授权规则等
5. **Seata Client 初始化（TM/RM）**
    - TM（事务发起方）和 RM（资源管理方）初始化
    - 连接到 Seata Server（TC）
6. **RabbitMQ 连接建立**
    - Producer/Consumer 建立连接与 Channel
    - 队列/交换机/绑定关系准备（有的项目会在启动时声明）

---

### 13.2 一次写请求的“主链路顺序”（从客户端到业务服务）

1. **客户端 → Gateway**（HTTP）
2. **Gateway 过滤器链**
    - 鉴权（JWT）
    - 限流（可在 Gateway 做一层 Sentinel）
    - 路由匹配：`/api/order/create` → `order-service`
3. **Gateway → Nacos 服务发现**
    - 获取 `order-service` 实例列表
4. **Gateway 负载均衡选实例并转发**
    - 选出一个 `order-service` 实例发起调用
5. **order-service 接收请求：Filter → Interceptor → Controller → Service**
    - 生成/透传 TraceId
    - 参数校验、鉴权结果落地（例如从 Token 拿 userId）

---

### 13.3 OpenFeign 调用链（order-service 调用 stock-service/account-service）

在 `orderService.createOrder()` 里，调用下游一般是：

1. **Sentinel（客户端侧）先拦一下（如果你对 Feign 做了整合）**
    - 判断是否触发限流/熔断
    - 如果触发：走降级（fallback）或直接抛异常
2. **OpenFeign 构造请求**
    - 把 Java 方法参数编码成 HTTP 请求（JSON）
    - 加上 Header（TraceId、token、X-Request-Id 等）
3. **Nacos + LoadBalancer 选实例**
    - 对 `stock-service` 做服务发现、选一个实例
4. **发起 HTTP 调用**
    - 连接池拿连接 → 请求发送 → 等响应
5. **超时控制**
    - 超时会抛异常（常见：ReadTimeout）
6. **返回解码**
    - JSON → Java 对象

> 建议：Feign 写请求最好配合“幂等号”，否则重试/超时会导致重复扣库存等事故。
> 

---

### 13.4 Sentinel 在整条链路中的位置（你会在多处看到它）

Sentinel 可能出现在：

- **Gateway 层**：挡掉入口洪峰（保护全系统）
- **服务间调用层（Feign）**：保护下游（防止雪崩）
- **业务方法层（@SentinelResource）**：保护关键业务方法（热点参数限流）

典型执行顺序（以 Feign 调用为例）：

1. 进入 Sentinel 资源
2. 判断：是否限流 / 是否熔断打开
3. 允许通过 → 执行真实远程调用
4. 统计 RT/异常比例 → 更新熔断状态
5. 若触发规则 → 走 fallback/异常返回

---

### 13.5 Seata 分布式事务顺序（强一致链路的“加戏点”）

如果你用 Seata（AT 模式最常见）来保证“扣库存 + 创建订单 + 记账”一致性，大致顺序是：

1. **入口服务开启全局事务（TM）**
    - `@GlobalTransactional` 标注的方法开始执行
    - TM 向 TC（Seata Server）申请一个 `XID`
2. **本地 DB 操作变成分支事务（RM）**
    - order-service 写订单表：RM 向 TC 注册分支事务
    - stock-service 扣库存：RM 注册分支事务
    - account-service 记账：RM 注册分支事务
    - AT 模式下会生成 undo_log（回滚用）
3. **业务正常结束：提交全局事务**
    - TM 通知 TC：全局提交
    - TC 通知各 RM：提交分支（AT 提交一般很快）
4. **中途任何一步异常：回滚全局事务**
    - TM 通知 TC：全局回滚
    - TC 通知 RM：根据 undo_log 回滚

重要注意点（非常常考）：

- Seata 会让链路“变长”，性能要评估
- 远程调用超时、重试、幂等等要和 Seata 配合好
- 不要把 RabbitMQ 这种“异步消息”当作分布式事务的一部分强行硬塞进 Seata

---

### 13.6 RabbitMQ 在链路中的位置（异步后续，而不是主链路）

一般推荐：主链路完成后发消息（最终一致/解耦）。顺序通常是：

1. order-service 主链路（可能含 Seata）完成关键写库
2. **发送 MQ 消息**（如 `OrderCreated`）
    - Producer publish → exchange → route → queue
3. **消费者服务异步消费**
    - Consumer 收到消息 → 执行本地事务（发券/积分/通知/物流等）
4. 消费成功 ACK；失败重试/进入死信队列

关键点：

- MQ 负责“把后续步骤变成异步”，不是让主链路更复杂
- 要做：消息幂等（去重）、消费重试策略、死信队列、消息可靠投递（例如本地消息表/Outbox）

---

## 14. 一张“顺序速记表”（你背这个就够用）

- **服务发现/路由**：Gateway → Nacos → LoadBalancer
- **服务内执行**：Filter → Interceptor → Controller → Service
- **远程调用**：Sentinel（判定）→ Feign（构造请求）→ Nacos/LB（选实例）→ HTTP（调用）→ 解码
- **分布式事务**：TM 开全局事务 → RM 注册分支 → TC 协调提交/回滚
- **消息异步**：主链路完成 → RabbitMQ publish → Consumer 执行业务 → ACK/重试
